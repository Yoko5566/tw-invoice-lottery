# 維護與營運手冊

本文件記錄最可能產生錯誤的外部依賴、靜默失敗模式及固定維護節奏。優先順序依「錯誤機率 × 未被發現時的損害」排列。

## 維護原則

1. 抓取失敗必須產生非零 exit code，並通知維護者；只做定時執行、不處理失敗，不算監控。
2. 規則與日期計算必須使用固定官方案例做回歸測試；編譯成功不能證明答案正確。
3. 介面必須顯示資料期別、資料產生時間與資料來源，不能讓舊資料看起來仍是最新資料。
4. 遠端更新驗證失敗時，不覆寫目前可用資料；繼續使用本機或內嵌資料並清楚顯示警告。
5. 真實發票樣本與官方頁面／PDF fixture 是維護資產；應保護隱私、保留來源與預期結果。

## 一級風險：官方網頁爬蟲

### 失敗模式

- `lastNumber.html` 改版後，使用 `href` 對應本頁檔名的期別定位規則失效。
- 導覽列同時存在當期與上一期標題，解析器抓到錯誤期別。
- 抓取失敗但仍沿用舊資料，使用者無法分辨資料已過期。

目前最重要的保護是：官方頁面領獎期間必須與本機推算結果完全一致，不一致就中止。

### 必要維護

- 每個開獎月（1、3、5、7、9、11 月）25 日後 24 小時內執行一次驗證。
- GitHub Actions 應安排 25～27 日重試窗口，並保留 `workflow_dispatch` 供人工重跑。
- 失敗必須透過 GitHub 通知、建立 issue 或 webhook 推播；成功但期別未前進也視為失敗。
- 保存官方 HTML fixture，解析器修改後以舊版與新版 fixture 同時測試。

### 目前缺口

目前 CLI 只有：

```text
twiv fetch [--out 路徑]
```

尚未實作 `twiv fetch --check`。在它完成前，不可把該指令直接寫進排程。暫時可將候選資料寫到獨立路徑，驗證成功後再發佈：

```powershell
.\twiv.exe fetch --out data\draws.candidate.json
```

正式的 check 模式至少必須確認：

- 抓取、解析及領獎期間交叉驗證全部成功。
- 最新期別符合目前日期預期；開獎後仍停在舊期別要回傳失敗。
- 候選資料不是空的，且不會在失敗時覆寫正式資料。

## 一級風險：期別、日期與法規規則

### 必測案例

- 開獎日為期別結束月的次月 25 日。
- 11～12 月期跨年到次年 1 月 25 日。
- 民國年與西元年互轉，例如 115 年對應 2026 年。
- 新年度第一期，例如 11601，無須人工新增硬編碼期別表。
- 特別獎、特獎、頭獎、二至六獎及增開六獎門檻。
- 所得稅、印花稅、領獎期間及買受人統編限制。

### 必要維護

- 將財政部公告案例保存成 golden fixtures，規則修改前後都跑回歸測試。
- 每次發版檢查官方規則公告；至少每六個月人工複核一次稅率、獎別與領獎規定。
- 規則來源、查核日期與依據網址要記錄在文件或 fixture metadata。

## 二級風險：真實發票 QR

目前測試只證明「生成的標準 QR 圖 → 解碼 → 欄位 → 期別 → 對獎」可行，不能推論真實照片準確率為 100%。

### 回歸樣本集

- 收集 5～10 張不同來源：四大超商、全聯、加油站、餐飲等。
- 每張至少保存清晰正拍；另保留斜拍、反光、裁切等失敗邊界樣本。
- 記錄預期的字軌、日期、隨機碼、金額及是否有買受人統編。
- 傳統三聯式、手開票、無 QR 小白單與舊格式應回傳「不支援或無法解析」，不可 panic。

發票可能包含交易與識別資訊。fixture 不應直接放進 Public repository；應去識別化、裁切或存於受控的 Private 測試資料庫。

## 二級風險：雲端發票 PDF 與索引

### 每期要檢查

- PDF 連結與檔名規則是否改變。
- PDF 是否仍為文字型、欄位順序是否相同。
- 各獎別解析筆數是否符合公告或合理範圍。
- 壓縮索引 encode／decode 後筆數與抽樣查詢是否一致。

### 保留政策

- 使用者端只保留當期與上一期索引。
- 更舊索引移至歸檔，不內嵌進單一執行檔。
- manifest 僅列出仍受支援的索引，避免每年增加約 60 MB 常駐資料。

## 二級風險：更新通道與供應鏈

### 必守條件

- manifest 入口 URL 固定在執行檔內。
- manifest 內的資料 URL 必須限制在允許的 HTTPS host／path；目前程式會直接採用 manifest 的 `dataset_url` 和雲端索引 `url`，尚缺 allowlist 驗證。
- 所有下載都驗 SHA-256；不符時拒絕寫入。
- 寫入應使用暫存檔與原子替換，避免中途中斷留下半份資料。
- 驗證失敗時保留前一版與內嵌保底資料。
- UI 永遠顯示：資料期別、`generated_at`、來源及雲端索引是否載入。

目前 UI 已顯示期別與來源，但尚未顯示 `generated_at`。

## 三級風險：工具鏈與對外介面

- `Cargo.lock` 必須進版控。
- `rust-toolchain.toml` 目前使用浮動的 `stable`；第一個可重現 Release 後應鎖定實際驗證過的 Rust 版本。
- Linux GNU 產物仍依賴目標機的 glibc。應聲明最低 glibc 版本並在舊發行版測試，或另外提供 musl 產物。
- 每六個月執行一次 `cargo audit`，並檢查依賴更新。
- 每六個月檢查 MCP 協定、ChatGPT／Codex 連接方式及 OpenAPI 3.1 schema 相容性。
- 正式散布 Windows 成品時評估程式碼簽章，降低 Smart App Control／防毒攔截機率。

## 固定維護節奏

| 時間 | 動作 | 失敗條件 |
|---|---|---|
| 每個開獎月 25～27 日 | 抓取官方一般獎、交叉驗證期別與領獎期間 | 抓取失敗、期別未前進、交叉驗證不符 |
| 每期 | 解析雲端 PDF、比對筆數、產生索引與 SHA-256 | 連結／排版改變、筆數異常、索引 round-trip 不一致 |
| 每次發版 | 全部單元測試、fixture、真實 QR 回歸、更新通道 smoke test | 任一測試失敗或資料時間未顯示 |
| 每六個月 | 法規複核、`cargo audit`、MCP／OpenAPI 相容性檢查 | 官方規則或介面已變更但文件／程式未更新 |
| 每年 | 檢查跨年期別、索引保留政策、最低支援作業系統 | 新年度期別推算錯誤或資料無限累積 |

## 最低維護集合

若只能持續做三件事：

1. 維護真實發票 QR 回歸樣本集。
2. 開獎後自動驗證 fetch，失敗或期別未前進時通知。
3. 介面永遠顯示資料期別、抓取時間與來源。
